# V15 Jetson / G474 USB Implementation Plan

> **For agentic workers:** Use superpowers:executing-plans for root integration; independent protocol/C tasks may use superpowers:dispatching-parallel-agents.

**Goal:** 준비된 ROS2 Jazzy/Ubuntu24.04/Orin Nano Super 배포 묶음과 STM32G474 USB 명령/피드백 규약을 실제 테스트 가능한 상태로 만든다.

**Architecture:** 기존 CAD 제어기는 보존한다. 새 USB gateway와 sensor synchronizer를 추가하고 공통 C parser/watchdog를 MCU 포트에 연결할 수 있게 한다. 동일 바이너리 명령 경로를 Isaac Sim에서 검증한다.

**Tech Stack:** Python3.12/3.11, ROS2 Jazzy, pyserial, C11, STM32Cube HAL integration hooks, Torch CPU, Pinocchio, Isaac Sim/Slurm.

**Spec:** `docs/superpowers/specs/2026-10-12-v15-jetson-usb-design.md`

## Global Constraints

- 원본 model15699/동결 student/물리/제어 계약 보존, 자동 commit/flash/deploy 금지.
- USB v1 header22bytes/CRC16-CCITT-FALSE/payload<=256, canonical SI 좌표.
- enable_motors=false 기본, 명시적 보정 필요. 호스트50ms/MCU100ms watchdog.
- GPU 검증 ws1 Slurm compute/QoS admin. held/unrelated jobs 보존.
- 기존 작업 디렉터리에서 새 패키지와 명시적 검증 어댑터만 추가.

## Review Focus

- 분할 프레임과 손상된 길이 뒤 정상 프레임의 회복 → Python/C parser 테스트.
- 오래된 session·sequence 재전송으로 watchdog이 갱신되는 오류 → replay/timeouts/wrap 테스트.
- 목표각과 게인의 서로 다른 stamp 결합 → atomic matcher 테스트.
- 센서가 안 오거나 시각이 미래/누락인데 명령이 계속 나가는 오류 → freshness/grid 테스트.
- 배포 묶음에 ws1/Isaac 의존이 남는 오류 → 압축 해제 후 import 및 실제 ROS2/Isaac 경로 테스트.

## Execution

사용자가 Ubuntu24.04/Orin Nano Super/G474를 확정하고 나머지 선택을 위임했다. 준비 작업은 계속 실행하며, 실제 Jetson 전송과 모터 활성화는 추후 요청 시 수행한다.

## 확인된 결과 (2026-10-12)

- 로컬 Python3.12 범위별 시험 117개 통과: protocol92/core13/PTY codec1/builder11.
- ws1 native Jazzy/Python3.11 시험 108개 통과: protocol92/core13/실제 ROS2 gateway PTY2/sensor_sync1.
  두 번째 gateway 시험은 Python 응답기를 거치지 않고 실제 C MCU emulator 프로세스를 연결한다.
- C core12 및 HAL stub4 통과. HAL branch는 제공한 mock main.h로 호스트 컴파일·실행했고,
  실제 ST HAL/CubeMX 빌드·G474 IRQ 성능·플래싱을 검증한 것은 아니다.
  Native emulator5/교차 언어3(100개 난수 벡터), core/HAL의 ASan+UBSan16도 통과했다.
- 독립 review의 잘린 큰 프레임 뒤 복구, 현재-session HELLO 재전송, float32 토크 경계,
  HAL logical5ms stamp 및 새 ISR fault 보존을 회귀로 재현 후 수정했다.
- 압축 해제한 번들만 PYTHONPATH에 넣어 실제 actor/student 추론과 CAD13body/23.094498kg 모델을 초기화했다.
  HardwareController의 초기 SIT와 0.5s 보행 명령 만료를 확인했다. simulator 모듈 import는 없었다.
  x86 CPU 시험이며 Jetson ARM 성능이나 실제 센서 검증으로 해석하지 않는다.
- 새 USB codec 물리 시험은 Slurm2355(평지/10cm/18cm 통합), compute/QoSadmin/shard1/mem13G로 제출했다.
  ws1의 다른 작업이 RAM28GB/30GB를 예약해 아직 PENDING이다. 기존 최적화의 비계단9/9 결과와 구분한다.
  먼저 잘못 제출된 중복2354만 실행 전에 취소했고 다른 사용 중인 작업은 보존했다.
- 전체 저장소 pytest는 Torch 미설치 및 보관된 테스트의 import 중복으로252개 수집 오류를 냈다.
  전체 로그를 보존했으며 위 숫자는 이번 변경 범위의 명시적 시험 결과다.

검증 로그는 `reports/v15/jetson_usb_20261012/verification/`에 있다.
실모터 CAN callback, 보정 ID/부호/영점, 실제 센서 입력과 Jetson에서의 colcon/주기 측정은 실기 단계에 남는다.

## 추가 물리 결과·영상 (2026-10-12 12:40 KST)

2355는 FAILED2:0이며 평지14s와18cm 통합30s를 통과했다. 10cm 통합은19.04s에 몸통 높이0.2m 미만으로
중단됐고 비인접 자가 접촉375.58N을 기록했다. 이 실패를 원래9/9 결과에 합쳐 숨기지 않는다.
공통 소스281개와 checkpoint는 기존2343과 동일하다. 기존6000틱 명령을 wire pack/unpack으로 재생했을 때
최종float32 qtarget/FF/gain/maxForce 차이는0이었다. 그러나 sit의 worldX는 기존60m/USB30m이며,
이전 시험·reset 이력도 달라 첫 physics step부터 미세한 차이가 났다. 원점이 유일원인이라 단정하지 않는다.

기존2343과 같은 `rough,standing_hold,sit_rise_walk_stop_sit,deep_crouch_rise_walk_stop_sit` 전체 순서로
비교2424를 제출했다(compute/QoSadmin/shard1/mem13G). 현재 다른 작업이CPU20/20을 사용해PENDING이다.
판정·제어 코드 수정 없이 실험 조건부터 맞춘다. `usb2355_origin_diagnosis.json`에 CPU 진단을 기록했다.
최신 평지의 실제 녹화로22초 미리보기(원속도14초+원본4–8초를0.5배속)를 만들었다.

## 조건을 맞춘 결과와 실패 대조 (2026-10-12)

2424는13:39:21–13:51:40 KST에 실제 실행돼COMPLETED0:0, 4/4 통과했다.
원래2343과 공통281소스 및 checkpoint가 같고 물리 상태·접촉·적용 명령·토크는 bit-identical이다.

몸통↔앞오른쪽정강이 접촉과 몸통 높이 실패를 보였다. 공통284소스와 checkpoint가 같고

lockstep Isaac 통과로50Hz 실기 주기가 검증됐다고 하지 않는다. 지지 회복과WBC 속도 최적화가 남는다.
